# Hajeen AI Production Authentication

## نطاق التنفيذ

يعتمد Backend الآن على مخزن SQLAlchemy دائم بدلاً من `_USERS` داخل الذاكرة. المخطط موجود في `api/v1/auth/models.py` ويضم حساب Hajeen الأساسي، هويات Google/Facebook/Email، جلسات refresh قابلة للإبطال، رموز التحقق وإعادة التعيين، وسجل تقييد محاولات المصادقة.

> لا تُحفظ كلمات المرور أو رموز OTP بصورتها الأصلية. تُحفظ كلمات المرور عبر bcrypt، وتُحفظ الرموز كـ hash مع مدة صلاحية وعدد محاولات.

## التدفقات

| التدفق | السلوك |
|---|---|
| التسجيل بالبريد | ينشئ الحساب بحالة غير مفعلة، ويرسل OTP إلى البريد المدخل بعد تطبيعه، ولا يصدر جلسة قبل التحقق. |
| الدخول بالبريد | يتحقق من الحساب النشط والبريد الموثق ووجود password identity؛ الخطأ عام لتقليل enumeration. |
| Google/Facebook | يتحقق الخادم من token عبر المزود، ثم يبحث عن `provider + subject` أو يربط البريد الموثق بالحساب الموجود بدلاً من إنشاء حساب مكرر. |
| refresh | يتحقق من JWT ثم من جلسة refresh الدائمة، ويدوّر الجلسة ويُبطل القديمة. |
| logout/revoke | يبطل جلسة refresh الحالية أو الجلسة المحددة، بينما إعادة تعيين كلمة المرور تبطل كل جلسات المستخدم. |
| forgot/reset | يعيد رسالة عامة للحالتين الموجود وغير الموجود، ويرسل OTP فقط للحساب الذي يملك password، ثم يستهلك الرمز ويغير كلمة المرور. |

## إعداد الإنتاج

يجب توفير `DATABASE_URL` لقاعدة MySQL/PostgreSQL دائمة، و`JWT_SECRET` عشوائي لا يقل عن 32 بايت، و`SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_EMAIL`. لا توجد قيمة fallback لبريد المسؤول؛ `To` دائماً هو بريد المستخدم المطبع. يمكن ضبط `AUTH_CODE_TTL`, `AUTH_CODE_MAX_ATTEMPTS`, `ACCESS_TOKEN_TTL`, و`REFRESH_TOKEN_TTL` وفق سياسة التشغيل.

في MySQL، يتولى `shared/database.py` تحويل `mysql://` إلى `mysql+pymysql://` مع `pool_pre_ping=True`. عند تشغيل النسخة لأول مرة ينشئ الراوتر جداول المصادقة عبر `Base.metadata.create_all`; يجب في بيئة الإنتاج تشغيل ذلك خلال نافذة نشر مضبوطة أو تحويله إلى migration مُدار قبل أول deploy متعدد النسخ.

## التحقق المنفذ

تم تشغيل `compileall` على طبقات API والأمان والدماغ. كما نجحت 9 اختبارات مصادقة تشمل التسجيل المعلّق حتى OTP، تطبيع المستلم، منع إرسال رمز للحساب غير الموجود، التقييد، bcrypt، تدوير refresh، logout، إبطال الجلسات بعد reset، واستمرارية الهوية.

لا يمكن اعتبار اختبارات Google/Facebook الحية أو إرسال SMTP الحقيقي ناجحة من بيئة الاختبار المحلية دون tokens وحسابات ومزود SMTP فعليين. اختبارات تلك التكاملات يجب تشغيلها في CI أو staging بأسرار injected، مع عدم وضع الأسرار في Git.

## ملاحظات الترحيل

إذا كانت هناك بيانات مستخدمين من مخزن قديم، يجب تحويلها مرة واحدة إلى `auth_users` و`auth_identities` مع سياسة واضحة للحسابات التي لا تملك بريداً موثقاً. لا يجوز تحويل SHA-256 إلى bcrypt دون معرفة كلمة المرور؛ يجب إجبار المستخدم على reset أو استخدام migration-on-login مؤقتة ومراجعة أمنية.
